# Отчёт по практической №1 — Lakehouse (MinIO → Lakekeeper → Trino)

---

## 1. Вариант и масштаб

| Поле | Значение |
| :---- | :---- |
| ФИО (как в VK Education) | Даурцев Егор |
| Вариант (запрос) | Q16 «Parts/Supplier Relationship» |
| Масштаб `sfN` | sf10 |
| Почему выбрал такой масштаб | Q16 использует только `part`, `partsupp` и `supplier` — самые «лёгкие» таблицы TPC-H (тяжёлый `lineitem` не нужен). На sf1 у `partsupp` всего 800 тыс. строк: всё читается за доли секунды из памяти, и разница между кодеками сжатия и эффект партиционирования тонут в накладных расходах на планирование запроса. На sf10 это 2 млн строк `part` и 8 млн строк `partsupp` — уже сотни мегабайт сырых данных, разница в размере и времени становится измеримой. sf100 (80 млн строк `partsupp`) для одноузлового Trino в Docker на ноутбуке избыточен: долгая генерация, упор в heap JVM и диск, а новых выводов для этого запроса он не даёт. |


## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO (форк Silo, `pgsty/silo`) | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Полностью совместим с S3 API: тот же конфиг Trino/Lakekeeper без изменений заработает с AWS S3 или Yandex Object Storage — лабораторный стенд переносится в облако заменой endpoint. Один контейнер, есть веб-консоль для просмотра файлов. Форк Silo взят потому, что официальные образы MinIO больше не раздаются бесплатно, а Silo — открытый и совместимый по портам, переменным и консоли. Альтернатива HDFS тяжелее (NameNode + DataNode) и не нужна для одного узла. |
| PostgreSQL 17 | БД, где Lakekeeper хранит метаданные каталога | Iceberg требует атомарной смены указателя на текущий `metadata.json` при коммите — Postgres даёт это транзакциями. Это основной поддерживаемый бэкенд Lakekeeper, надёжный и знакомый, легко посмотреть содержимое каталога обычным SQL. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует открытую спецификацию Iceberg REST Catalog, поэтому одни и те же таблицы видят Trino, Spark, StarRocks, PyIceberg — каталог не привязан к движку. Написан на Rust: один лёгкий контейнер, быстрый старт. Hive Metastore тяжелее (JVM, Thrift, не REST), Nessie добавляет git-подобное ветвление, которое здесь не нужно, AWS Glue — только облако и платный. |
| Trino 476 | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | MPP SQL-движок с полноценным Iceberg-коннектором: CTAS, INSERT/DELETE/MERGE, партиционирование, time travel, schema evolution, метатаблицы `$files`/`$snapshots`. Встроенный коннектор `tpch` генерирует данные на лету — ничего не надо скачивать. Работает интерактивно на одном узле; Spark для такой задачи тяжелее и ориентирован на батчи, а не на быстрые ad-hoc запросы. |
| Metabase (BI) | отчёт/дашборд поверх данных lakehouse | Поднимается одним `docker run` без сборки образа, драйвер Starburst/Trino встроен «из коробки» (Superset требует доустанавливать python-драйвер `trino` в образ). Подключается к Trino как к единой точке входа, поэтому видит все слои — Bronze, Silver и Gold. |

### Скрипты, которыми поднимал стек


```sh
mkdir -p ~/lakehouse/catalog && cd ~/lakehouse

# MinIO (форк Silo) — объектное хранилище, S3 API на :9000, консоль на :9001

  -p 9000:9000 -p 9001:9001 \

  -e MINIO_ROOT_PASSWORD=minioadmin \

# PostgreSQL — хранилище метаданных Lakekeeper
docker run -d --name lakehouse-pg \
  -e POSTGRES_PASSWORD=postgres \

# Миграции схемы Lakekeeper в Postgres (одноразово)

  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' \
  -p 8181:8181 \

# Принять ToU и зарегистрировать warehouse "demo" → бакет warehouse в MinIO
curl -X POST http://localhost:8181/management/v1/bootstrap \
  -H "Content-Type: application/json" -d '{"accept-terms-of-use": true}'

iceberg.rest-catalog.uri=http://host.docker.internal:8181/catalog

fs.native-s3.enabled=true

s3.path-style-access=true

s3.aws-access-key=minioadmin
s3.aws-secret-key=minioadmin

echo 'connector.name=tpch' > catalog/tpch.properties

# Trino — SQL-движок на :8080
docker run -d --name trino --add-host host.docker.internal:host-gateway \
  -p 8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog" \
  trinodb/trino:476
```


## 3. Разбор запроса какие данные нужны

Запрос Q16 считает, сколько разных поставщиков у деталей в разрезе бренд/тип/размер, исключая поставщиков с жалобами клиентов.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| `part` | `partkey`, `brand`, `type`, `size` | `partkey` — ключ джойна с `partsupp`. `brand` — фильтр `<> 'Brand#45'`, `type` — фильтр `NOT LIKE 'MEDIUM POLISHED%'`, `size` — фильтр `IN (49, 14, 23, 45, 19, 3, 36, 9)`; все три — ключи `GROUP BY`, сортировка и вывод. |
| `partsupp` | `partkey`, `suppkey` | `partkey` — джойн с `part`. `suppkey` — анти-джойн (`NOT IN` подзапроса) и агрегат `count(DISTINCT suppkey)`. |
| `supplier` | `suppkey`, `comment` | Только подзапрос: `comment LIKE '%Customer%Complaints%'` отбирает поставщиков с жалобами, `suppkey` — их список для исключения. На sf10 таких поставщиков 50 (по спецификации TPC-H — 5 × SF). |


## 4. Медальон решения по каждому слою

Общая идея: **Bronze** неизменённая копия источника, **Silver** очищенная и уже связанная таблица «деталь ↔ поставщик» без поставщиков с жалобами, переиспользуемая для любых запросов по деталям, **Gold** готовый ответ Q16. Фильтры именно Q16 (бренд/тип/размеры) применяются только в Gold, чтобы Silver оставался универсальным.

### SQL построения слоёв

```sql
CREATE SCHEMA IF NOT EXISTS lakekeeper.bronze;
CREATE SCHEMA IF NOT EXISTS lakekeeper.silver;
CREATE SCHEMA IF NOT EXISTS lakekeeper.gold;

-- ===== BRONZE: сырая копия источника, все колонки =====
CREATE TABLE lakekeeper.bronze.part
WITH (format = 'PARQUET') AS
SELECT * FROM tpch.sf10.part;

CREATE TABLE lakekeeper.bronze.partsupp
WITH (format = 'PARQUET') AS
SELECT * FROM tpch.sf10.partsupp;

CREATE TABLE lakekeeper.bronze.supplier
WITH (format = 'PARQUET') AS
SELECT * FROM tpch.sf10.supplier;

-- ===== SILVER: связка деталь↔поставщик без поставщиков с жалобами =====
CREATE TABLE lakekeeper.silver.part_supplier
WITH (
  format       = 'PARQUET',
  partitioning = ARRAY['size'],
  sorted_by    = ARRAY['brand', 'type']
) AS
SELECT ps.partkey,
       ps.suppkey,
       p.brand,
       p.type,
       p.size
FROM lakekeeper.bronze.partsupp AS ps
JOIN lakekeeper.bronze.part     AS p ON p.partkey = ps.partkey
WHERE ps.suppkey NOT IN (
  SELECT suppkey
  FROM lakekeeper.bronze.supplier
  WHERE comment LIKE '%Customer%Complaints%'
);

-- ===== GOLD: витрина-ответ на Q16 =====
CREATE TABLE lakekeeper.gold.q16_supplier_cnt
WITH (format = 'PARQUET') AS
SELECT brand,
       type,
       size,
       count(DISTINCT suppkey) AS supplier_cnt
FROM lakekeeper.silver.part_supplier
WHERE brand <> 'Brand#45'
  AND type NOT LIKE 'MEDIUM POLISHED%'
  AND size IN (49, 14, 23, 45, 19, 3, 36, 9)
GROUP BY brand, type, size;

-- Чтение витрины в порядке, который требует Q16
SELECT * FROM lakekeeper.gold.q16_supplier_cnt
ORDER BY supplier_cnt DESC, brand, type, size;
```

**Проверка корректности** Gold должен совпасть с эталонным Q16 на исходных данных (оба запроса возвращают 0 строк):

```sql
WITH ref AS (
  SELECT p.brand, p.type, p.size, count(DISTINCT ps.suppkey) AS supplier_cnt
  FROM tpch.sf10.partsupp ps JOIN tpch.sf10.part p ON p.partkey = ps.partkey
  WHERE p.brand <> 'Brand#45' AND p.type NOT LIKE 'MEDIUM POLISHED%'
    AND p.size IN (49, 14, 23, 45, 19, 3, 36, 9)
    AND ps.suppkey NOT IN (SELECT suppkey FROM tpch.sf10.supplier
                           WHERE comment LIKE '%Customer%Complaints%')
  GROUP BY p.brand, p.type, p.size
)
SELECT * FROM ref EXCEPT SELECT * FROM lakekeeper.gold.q16_supplier_cnt
UNION ALL
SELECT * FROM lakekeeper.gold.q16_supplier_cnt EXCEPT SELECT * FROM ref;
```

**Как снимал метрики:**

```sql
SELECT count(*) FROM lakekeeper.bronze.part;   -- строки
SELECT round(sum(file_size_in_bytes) / 1048576.0, 1) AS size_mb
FROM lakekeeper.bronze."part$files";           -- вес файлов данных в MinIO, МБ
SHOW CREATE TABLE lakekeeper.bronze.part;      -- формат, сжатие, партиционирование
```

| `silver.part_supplier` | `partkey, suppkey, brand, type, size` | 7995520 | 42.2    | PARQUET | ZSTD   | `size` (+ сортировка внутри файлов по `brand, type`) | Это «очищенный» факт: уже исключены поставщики с жалобами и выполнен джойн, так что следующим слоям не нужен ни `supplier`, ни повторный джойн. Оставлены только колонки, имеющие смысл для анализа связей деталь–поставщик; длинные `comment`, `name` и т.п. отброшены — вес таблицы в разы меньше Bronze. Партиция по `size`: 50 значений по ~160 тыс. строк — файлы нормального размера, а Q16 фильтрует 8 размеров из 50, и Trino читает только 8 партиций (≈16% данных) за счёт partition pruning. Сортировка по `brand, type` даёт узкие min/max-статистики в parquet и лучше сжимает повторяющиеся строки. Фильтры бренда/типа Q16 намеренно не применены — Silver переиспользуем для других запросов по деталям. |

## 5. Тесты производительности

Методика: собираю две копии Bronze — в схемах `bronze_gzip` и `bronze_zstd` — меняя только кодек, затем гоняю на каждой исходный Q16 (с `tpch.sf10` → `lakekeeper.bronze_<codec>`) 5 раз и беру медиану; первый «холодный» прогон не учитываю.

```sql
CREATE SCHEMA IF NOT EXISTS lakekeeper.bronze_gzip;
SET SESSION lakekeeper.compression_codec = 'GZIP';
CREATE TABLE lakekeeper.bronze_gzip.part     AS SELECT * FROM tpch.sf10.part;
CREATE TABLE lakekeeper.bronze_gzip.partsupp AS SELECT * FROM tpch.sf10.partsupp;
CREATE TABLE lakekeeper.bronze_gzip.supplier AS SELECT * FROM tpch.sf10.supplier;

CREATE SCHEMA IF NOT EXISTS lakekeeper.bronze_zstd;
SET SESSION lakekeeper.compression_codec = 'ZSTD';
CREATE TABLE lakekeeper.bronze_zstd.part     AS SELECT * FROM tpch.sf10.part;
CREATE TABLE lakekeeper.bronze_zstd.partsupp AS SELECT * FROM tpch.sf10.partsupp;
CREATE TABLE lakekeeper.bronze_zstd.supplier AS SELECT * FROM tpch.sf10.supplier;

-- Размер слоя целиком, МБ (аналогично для bronze_zstd)
SELECT round((
    (SELECT sum(file_size_in_bytes) FROM lakekeeper.bronze_gzip."part$files")
  + (SELECT sum(file_size_in_bytes) FROM lakekeeper.bronze_gzip."partsupp$files")
  + (SELECT sum(file_size_in_bytes) FROM lakekeeper.bronze_gzip."supplier$files")
) / 1048576.0, 1) AS bronze_mb;

-- Время прогонов Q16
SELECT query_id,
       date_diff('millisecond', created, "end") AS elapsed_ms,
       substr(query, 1, 80) AS query
FROM system.runtime.queries
WHERE state = 'FINISHED' AND query LIKE '%supplier_cnt%'
ORDER BY created DESC;
```

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему)                                                                                                                                                                                                                 |
| :--------------- | :------------ | :---------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GZIP             | 1241          | 293.4             | GZIP (deflate) сжимает примерно на уровне ZSTD, но распаковывается заметно медленнее и сильно медленнее пишется: при каждом чтении CPU тратит больше времени на декомпрессию. Имеет смысл только для холодного архива, который почти не читают. |
| ZSTD             | 1072          | 293.4             | ZSTD даёт сопоставимый или меньший размер при более быстрой распаковке и записи, поэтому для слоя, который регулярно читают при пересборке Silver, это лучший баланс места и скорости. Именно его я оставил основным кодеком на всех слоях.     |


## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная OLTP-база (Postgres) хранит данные построчно и рассчитана на точечные операции; аналитика по сотням миллионов строк упирается в один сервер, его диск и CPU, а масштабировать хранение и вычисления по отдельности нельзя. Классический DWH решает аналитику, но дорогой, проприетарный и держит данные в своём закрытом формате. Lakehouse разделяет слои: данные лежат в открытом колоночном формате (Parquet) в дешёвом объектном хранилище, которое масштабируется почти бесконечно; Iceberg поверх файлов даёт то, чего у «голого» data lake не было — транзакции, схему, снапшоты, time travel, эволюцию схемы; а вычисления (Trino, Spark, StarRocks) подключаются к тем же таблицам независимо и масштабируются отдельно. В итоге — SQL и надёжность хранилища по цене и гибкости озера, без привязки к одному вендору. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | `ALTER TABLE lakekeeper.silver.part_supplier ADD COLUMN load_ts timestamp(6) with time zone;` — операция мгновенная: Iceberg пишет новый `metadata.json` с новой схемой, существующие parquet-файлы не переписываются, для старых строк `load_ts` читается как `NULL`, новые вставки заполняют колонку. `ALTER TABLE lakekeeper.silver.part_supplier RENAME COLUMN type TO part_type;` — тоже только метаданные: Iceberg адресует колонки по внутреннему field id, а не по имени, поэтому старые файлы, где колонка физически называется `type`, продолжают корректно читаться как `part_type`. Проверял через `SHOW CREATE TABLE` и `SELECT * FROM "part_supplier$snapshots"` — в MinIO появился только новый файл метаданных, данные не тронуты. Gold после переименования нужно пересобирать с новым именем колонки. |
| Пример скрипта восстановления данных из снапшота (time travel) | См. скрипт ниже. |

```sql
-- 1. Запоминаем текущий снапшот
SELECT snapshot_id, committed_at, operation
FROM lakekeeper.silver."part_supplier$snapshots"
ORDER BY committed_at DESC;

-- 2. «Авария»: удалили лишнее
DELETE FROM lakekeeper.silver.part_supplier WHERE size = 14;
SELECT count(*) FROM lakekeeper.silver.part_supplier WHERE size = 14;   -- 0

-- 3. Time travel: смотрим таблицу на момент до удаления
SELECT count(*)
FROM lakekeeper.silver.part_supplier FOR VERSION AS OF <snapshot_id>
WHERE size = 14;                                                          -- строки на месте

-- 4а. Восстановление откатом таблицы на снапшот
ALTER TABLE lakekeeper.silver.part_supplier
EXECUTE rollback_to_snapshot(<snapshot_id>);
-- (в старых версиях Trino:
--  CALL lakekeeper.system.rollback_to_snapshot('silver', 'part_supplier', <snapshot_id>);)

-- 4б. Либо точечное восстановление только удалённых строк, без отката остальных изменений
INSERT INTO lakekeeper.silver.part_supplier
SELECT * FROM lakekeeper.silver.part_supplier FOR VERSION AS OF <snapshot_id>
WHERE size = 14;
```


### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Metabase (BI) | Задача — показать, как бизнес-пользователь работает с данными lakehouse, и BI для этого нагляднее движка. Metabase поднимается одним контейнером, драйвер Starburst (Trino) встроен — не нужно собирать свой образ, как для Superset. Подключение идёт через Trino, поэтому Metabase сразу видит все схемы каталога `lakekeeper` (bronze/silver/gold) без отдельной настройки S3 и REST-каталога. Есть и визуальный конструктор вопросов, и SQL-редактор. |

**Скрипт развёртывания:**

```sh
docker run -d --name metabase \
  --add-host host.docker.internal:host-gateway \
  -p 3000:3000 \
  -v metabase-data:/metabase-data \
  -e MB_DB_FILE=/metabase-data/metabase.db \
  metabase/metabase:latest
```

## 7. Выводы

Медальон разделяет ответственность: Bronze хранит неизменённую копию источника и позволяет пересобрать всё ниже без повторной загрузки, Silver делает тяжёлую работу один раз (очистка от поставщиков с жалобами и джойн 8 млн строк), а Gold превращает ответ на Q16 в мгновенное чтение крошечной таблицы. Колоночный Parquet позволяет хранить в Bronze все колонки почти бесплатно для чтения, а в Silver отбрасывание текстовых полей и партиционирование по `size` уменьшают объём сканирования до ~16% данных за счёт partition pruning. Для сжатия ZSTD оказался лучшим балансом размера и скорости распаковки по сравнению с GZIP, поэтому он используется на всех слоях. Iceberg поверх объектного хранилища дал то, чего нет у простого data lake: эволюцию схемы без переписывания файлов и восстановление данных из снапшотов.
